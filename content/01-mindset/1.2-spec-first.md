# Урок 1.2 — Сначала — спецификация

> **Зачем:** Когда начинаешь сразу делать — тратишь время на переделки. Когда сначала описываешь — Claude делает правильно с первого раза. Spec-first экономит в 3–5 раз больше времени чем кажется.

---

## Что такое Spec

Spec (спецификация) — текстовый документ на 10–15 строк, который отвечает на 5 вопросов **до** того как ты что-то просишь сделать.

```markdown
## Spec: [название проекта или задачи]

**Цель:** что мы хотим получить в итоге
**Пользователь:** кто будет этим пользоваться и зачем
**Входные данные:** что у нас есть на входе
**Результат:** как выглядит готовый вывод
**Ограничения:** что нельзя, какие рамки, что важно учесть
```

---

## Пример: плохо vs хорошо

**❌ Без spec — "просто попросил":**
```
Сделай инструмент для анализа отзывов конкурента.
```
Результат: Claude придумывает что-то своё. Не то что нужно.

**✅ С spec:**
```
Цель: получить структурированный список инсайтов из отзывов
Пользователь: менеджер по продукту, будет использовать для брифа команде
Входные данные: 50–100 отзывов в виде текста, вставляю вручную
Результат: три секции — топ-скарги, топ-плюсы, незакрытые потребности
Ограничения: каждая секция — не больше 5 пунктов, только факты без домыслов
```
Результат: Claude делает именно это. С первого раза.

---

> [!WARNING] Spot the Mistake
> Найди проблему в этой spec:
> ```
> Цель: сделать удобный инструмент для команды
> Пользователь: все в офисе
> Результат: что-то полезное
> Ограничения: не слишком сложно
> ```
>
> **Проблемы:** "удобный", "все в офисе", "что-то полезное", "не слишком сложно" — это не spec, это пожелания. Нет конкретики: что делает инструмент? какие данные? какой формат вывода? Без этого Claude будет угадывать.
